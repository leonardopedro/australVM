L10 Cycle B: the checker extended by code extracted from the total subset

The other half of L10, and the one that makes the subset worth having: not just a
language the *compiler* targets, but a language the *checker* can be extended
in.

## A measure library, proved

`lib/liquid/subset/liquid_measure.mlw` defines `weight` and `fuel` over
`list int` with structural recursion — the one recursion T2 admits and the only
kind docs/LIQUID.md §8.3 allows an emitted theory to contain. Its decreasingness
obligation is **proved by Why3** (`fuel_decreases_on_tail`, Valid), which is the
entire reason to do this in Why3 rather than in OCaml: the fold check below then
rests on a theorem rather than on an assumption.

## Reused the existing driver — no `liquid.drv`

The plan asks for `lib/liquid/liquid.drv`. It does not exist and I did not create
it: `lib/why3_plugin/unfer_ocaml.drv`, which unfer's S36 cycle already uses,
maps exactly this fragment (`int` to a native OCaml int, plus `bool` and
`list`). A second driver would have been a near-verbatim copy with a different
name — precisely the duplication to avoid. The new gate below fails if that
driver ever stops working, so the reuse is load-bearing and not taken on trust.

## The Why3 dialect notes are in the file, because three guesses were wrong

`list.List` in 1.8.x is an algebraic datatype (`Nil`/`Cons`), not the older
`[]`/`::` spelling; `length` lives in `list.Length`, not `list.List`; and a
`match` body needs `let rec function`. Each was a syntax error or an unbound
symbol, not anything subtle.

**One property is deliberately not claimed.** Additivity over concatenation is
true but needs induction, and `induction` is not in the subset — Alt-Ergo times
out on it (278k steps). Rather than leave a goal that fails forever, it is
recorded as a gap: a file whose stated obligations do not discharge teaches
readers to expect the check to be decorative. The subset supports *measures*
(properties holding by construction plus a decreasingness obligation), not
*inductive* properties.

## Checked in, and gated

`lib/liquid/LiquidMeasure.ml` is extracted output, checked in so dune can
compile it. A `verify-invariants` gate re-extracts and diffs, so it cannot drift
from the `.mlw` — which is what makes checking in generated code defensible. The
gate is stronger than the existing parse gate: extraction proves the source is
inside the extractable fragment *and* that the driver still matches the engine
(a Why3 upgrade that renames a theory breaks extraction before it breaks
parsing). Tested in both directions: passes clean, fails with exit 1 on a
deliberately corrupted golden.

## The pass, and a false positive my own test caught

`LiquidSubset.check` is registered through `Compiler_plugin.register_typed` as
tenant `liquid_measure`, beside `liquid`. Its first `is_fold_name` accepted any
name *ending* in "fold" — and the test caught it on **`unfold`**, a name that is
not a fold but does contain the letters. Now word-boundary aware, so `sum_fold`
matches and `unfold` does not. That was the right thing for the test to catch:
the pass only *reports* what it ranked, so a false positive is a misleading log
line, but it is still a lie about what was checked.

Also worth recording: `Compiler_plugin.list_registered` lists only *gate* names
— it filters `Typed` out — so the typed seam has to be read through `names`.
The test registering the pass itself is because `Vm_plugin.boot` does not run in
a test binary, so the production wiring is checked by `verify-invariants` instead
of left untested.
