The layout example needs a careful reading. `Layout.lean` uses a fixed
five-constructor state type and a concrete dictionary, plus finite bank-image
checks. Its `bank(x,y) = (2*x + 4*y) mod 32` collision survives **relabelling
bank numbers**. It does not rule out every transformation of addresses,
physical padding or lane-to-data assignment. New bank-conflict analyses must
state what their “swizzle” is allowed to change. Bank conflicts concern
performance; an in-bounds colliding read is not automatically an incorrect read.

## Why the typed frontend is the right source

`Stages.Tast` retains `Nat32`, `Float32`/`Float64`, resolved function/method IDs,
regions and source structure. `Compiler.compile_mod` currently performs typing,
plugins and linearity before extracting bodies and monomorphizing, then selects
CPS/Cranelift or C. Its CPS path can catch errors and fall back to C. A required
GPU target must select a separate path **before that fallback**.

CPS/CLIF is not a suitable initial GPU interface: the current bridge path does
not carry a device address-space model, workgroup semantics or the complete
source-width contract needed here. The older plan's suggestion to hang MLIR
from CPS is an architectural possibility, not a reason to discard typed
information already available earlier.

A small typed `KernelIR` should therefore be produced from checked Austral
functions. Its first memory-access pattern is generated by the compiler:
independent map/zip invocations, read-only inputs and one fresh output. Authors
write the actual scalar computation in Austral; the compiler emits the compute
entry wrapper and device code. That is genuine kernel generation even though
v1 does not expose arbitrary GPU pointers or barriers.

One useful finding is the existing `ModularArithmetic(Nat32)` instance in
`lib/builtin/Pervasive.{aui,aum}`. Its add/subtract/multiply operations give the
first backend an exact integer contract. Recognize those operations by resolved
builtin identity and type. Do not reinterpret `trappingAdd`, accept arbitrary
`@embed`, or whitelist user functions just because their names look familiar.
The generated `lib/BuiltInModules.ml` is not the source to edit.

## Backend comparison and decision

| Choice | Benefit | Cost or missing work | Decision |
|---|---|---|---|
| Typed KernelIR → WGSL → Naga/wgpu | Small textual emitter, adapter-independent validation, existing federation dispatch examples | Restricted scalar/numerical profile; does not provide every native GPU feature | First executable backend |
| KernelIR → MLIR `gpu`/`arith` → NVVM/PTX | Follows the original vision; path to NVIDIA-specific tuning and richer lowering | LLVM/MLIR version and pass pipeline, launch ABI, CUDA runtime and target/toolkit testing | Separate optional backend after first release |
| KernelIR → MLIR → SPIR-V | Could share a Vulkan execution route | Conversion legality, descriptor ABI and Naga/SPIR-V interoperability still need a measured prototype | Do not build alongside the first backend |
| KernelIR → CUDA C/NVRTC | Relatively small NVIDIA-specific emitter/runtime | Toolkit dependency and another runtime; no portable Vulkan route | Alternative if a measured workload later needs CUDA first |
| Emit Rust/CubeCL source | Reuses an established Rust GPU language | Generated Rust/macro compilation becomes another toolchain boundary | Integration option, not the initial compiler route |
| Direct SPIR-V or PTX encoder | Full control | High implementation and validation cost before any useful workload | Reject for the first implementation |

This choice preserves the **goal** of the old GPU plan while changing the first
implementation route. It does not require replacing Cranelift for CPU modules.
MLIR should be a later consumer of the same typed IR, not a prerequisite for
getting a generated kernel onto a device.

Primary sources checked on this date:

- [wgpu 29.0.4](https://docs.rs/wgpu/29.0.4/wgpu/): WGSL input and native backend support. The local velysterm lock already uses 29.0.4; do not copy examples from an unrelated latest API.
- [Naga 29.0.4](https://docs.rs/naga/29.0.4/naga/): parsing and validating shader IR without acquiring a device. Use validation capabilities matching the selected subset, rather than indiscriminately accepting all extensions.
- [WGSL specification](https://gpuweb.github.io/gpuweb/wgsl/): concrete integer arithmetic, floating-point limits, memory layout and uniformity rules. The integer-first subset avoids unnecessary floating-point and barrier obligations.
- [MLIR GPU dialect](https://mlir.llvm.org/docs/Dialects/GPU/): GPU kernels, launches and the NVVM lowering pipeline; compilation still needs a target and runtime.
- [MLIR LLVM translation](https://mlir.llvm.org/docs/TargetLLVMIR/) and [NVVM dialect](https://mlir.llvm.org/docs/Dialects/NVVMDialect/): lowering and translation are separate stages, with NVIDIA-specific address spaces and ABI considerations.
- [CubeCL](https://github.com/tracel-ai/cubecl): an existing Rust kernel/runtime alternative against which additional compiler complexity should be justified.
- [Digestif](https://github.com/mirage/digestif): use its SHA-256 implementation for the proposed OCaml bundle writer, with Rust independently reproducing the digest.

These references support the architecture comparison. They do not establish
performance or correctness of a not-yet-written backend.

The inspected host is aarch64. `mlir-opt`, `mlir-translate`, `nvcc`, `vulkaninfo`
and `nvidia-smi` were not on its current PATH. A DRM render node exists, but the
inspected sysfs driver was `msm_dpu`; that is not evidence of an operational
Vulkan compute adapter. Do not turn this into an assertion that no GPU exists.
G00 in the plan records actual adapter availability in the runtime environment.

The new runtime's separate Cargo lock should initially pin wgpu/Naga 29.0.4,
with optional device dependencies and no default dependency from the CPU JIT.
The unfer CUDA stack currently locks cudarc 0.13.9. Do not introduce an unrelated
cudarc generation into it when implementing a later CUDA backend.
